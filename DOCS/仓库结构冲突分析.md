# 仓库结构与当前冲突分析

**日期**：2026-08-08
**范围**：先阅读 `DOCS` 内架构、分层、协议、引脚、调试文档，再对照当前 `App/Bsp/Drivers/Middleware/Core` 与构建结果。

## 1. 文档定义的目标架构

目标是一个基于 **STM32H723 + AD9959** 的多用途数字发射机软件平台，遵循软件定义发射机思想，调制算法、DDS 命令、AD9959 驱动和 MCU 外设控制应解耦。

主数据流应为：

```text
Host Interface
  -> Command Parser
  -> Tx Manager
  -> Packet
  -> Symbol
  -> Pulse Shaping
  -> Modulator
  -> DDS_Command
  -> DDS Encoder
  -> DMA Buffer / Scheduler
  -> SPI DMA
  -> AD9959
```

分层依赖方向应为：

```text
App
  -> Middleware
  -> Drivers
  -> Bsp
  -> Core/HAL
```

核心约束：

- `Core` 只放 CubeMX 初始化和 HAL 入口，不放业务、算法、发送流程。
- `Bsp` 只封装 MCU 外设，不出现 DDS、调制、Profile 等业务概念。
- `Drivers/AD9959` 只负责器件寄存器访问、上电、复位、IO_UPDATE、Profile 等芯片级能力。
- `Middleware` 是发送流水线核心，应与具体硬件解耦。
- 目标硬件链路是定时器触发、双 SPI/DMA、乒乓缓冲、TIM8 延迟 IO_UPDATE。

## 2. 当前实现快照

当前工程可以编译通过：

```Shell
make -j4
text=42524, data=284, bss=5900
```

但有两个警告：

```text
Drivers/Trigger/trigger.c:24: unused variable 'lptim_period'
App/dds_control.c:93: unused variable 'tim8_cr1'
```

这说明当前问题不是简单的编译失败，而是多套架构路径并存、部分旧路径未被调用后被链接器丢弃。特别是 `Trigger`、双 SPI DMA、LPTIM/TIM2/TIM4 等目标链路仍有接口和代码残留，但主程序实际没有走这条链路。

## 3. 冲突清单

### C01：硬件时序主线在文档内部和代码之间不一致

目标文档主线写的是 `TIM2_CH1(PA0) -> DMA -> SPI1+SPI3`，`TIM2 Update -> TIM8 Reset`，`TIM4` 捕获 CS 时序；调试手册又引入 `LPTIM1/LPTIM3 -> DMAMUX Sync Gate`。当前代码实际启动的是 `TIM8` 自由运行中断：

- `Core/Src/main.c` 调用 `BSP_TIM8_StartFreeRun(10000U)`。
- `main.c` 中没有 `MX_TIM2_Init()`、`MX_TIM4_Init()`、`MX_SPI3_Init()`、`MX_LPTIMx_Init()`。
- `Core/Inc/main.h` 把 PA0 标为 `SYNC_LPTIM3_TO_TIM8_ETR`，不是文档里的 `SPI_9959_DMA_TRIG`。

影响：无法判断应恢复 TIM2 触发链路，还是恢复 LPTIM/DMAMUX gate 链路；后续驱动修改容易继续互相覆盖。

### C02：目标双 SPI DMA 被降级成 SPI1 阻塞发送

目标架构要求 SPI1+SPI3 双线并行，DMA 从乒乓缓冲搬运，TIM8 在 SPI 完成后输出 IO_UPDATE。当前主发送路径是在 `HAL_TIM_PeriodElapsedCallback(TIM8)` 里阻塞发送：

- `Core/Src/main.c` 在 TIM8 回调中调用多次 `HAL_SPI_Transmit(&hspi1, ...)`。
- `Bsp/bsp_spi.c` 明确写了 `SPI3 removed in downgrade mode`，`BSP_SPI_Both_DMA_Start()` 忽略 `spi3_buf`。
- `Drivers/AD9959/ad9959.c` 和 `Middleware/DDS/dds_encoder.c` 仍保留 SPI1/SPI3 双线说明。

影响：实时性、同步性和双线吞吐都不符合目标；`TIM4` 捕获出来的 CS 时序也不再代表 DMA 流水线。

### C03：`Bsp` 对外接口仍宣称支持 TIM2/TIM4/SPI3，但 CubeMX 当前没有对应 HAL 句柄

`Bsp/bsp_tim.c` 声明 `extern TIM_HandleTypeDef htim2;`、`htim4;`，但当前 `main.c` 只有 `htim5/htim8/htim15`。`Drivers/AD9959/ad9959.c` 声明 `extern SPI_HandleTypeDef hspi3;`，但当前 `main.c` 只有 `hspi1`。

当前能链接，是因为相关函数没有被主路径引用，并且 `-ffunction-sections` + `--gc-sections` 丢弃了未用函数。

影响：一旦调用 `Trigger_Init/Start` 或 `AD9959_Enable2BitSerial()`，就可能出现链接错误或运行期外设未初始化。

### C04：`Core/Src/main.c` 承载了过多业务和发送逻辑

文档要求 `Core` 不放业务代码。当前 `main.c` 直接包含并调度：

- AD9959 初始化、测试模式、IO_UPDATE GPIO/Timer 模式切换。
- 默认四通道 CW 配置。
- TIM8 ISR 中符号源生成、编码、逐寄存器 SPI 发送。
- Host protocol 和 DDSControl 主循环调度。

影响：CubeMX 重新生成时风险高；业务路径难以迁移、测试和复用；也破坏了 App/Middleware/Drivers 的职责边界。

### C05：中断上下文执行了重活和阻塞 HAL 调用

分层规范要求中断中只做置标志、简单计数、极短搬运。当前 TIM8 ISR 中执行：

- `SymbolSource_Generate()`
- `Encoder_BuildBank()`
- 每通道最多 4 次阻塞 `HAL_SPI_Transmit()`

影响：TIM8 频率越高越容易阻塞系统；UART DMA/协议处理、LED 刷新、后续调制计算都会受影响。当前 10 kHz 只是降级规避，不是目标方案。

### C06：`Middleware/DDS` 反向依赖 `Drivers/AD9959`

目标上 `Middleware/DDS` 应只把 `DDS_Command` 编成帧，不直接访问具体驱动。当前 `dds_encoder.c` 包含 `ad9959.h`，并在 `Encoder_WriteStaticRegs()` 中直接调用 `AD9959_WriteRegister()`。

影响：Encoder 无法替换到 AD9910、FPGA DDS 或其他发送后端；上层流水线和具体器件驱动耦合。

### C07：`App/dds_control.c` 直接操作 TIM8、SPI1 和 AD9959 GPIO 模式

`dds_control.c` 直接读写 `TIM8->ARR/CCR1/DIER/CR1`，检查 `HAL_SPI_GetState(&hspi1)`，并调用 `AD9959_IOUpdateGpioInit()`/`AD9959_IOUpdateTimerInit()` 抢占 PC6 模式。

影响：App 层越过 Trigger/BSP 管理硬件状态，和 TIM8 运行链路互相踩踏。APPLY 过程对实时发送链路是否安全，无法由单一模块保证。

### C08：AD9959 驱动职责过宽，混入多条实验路径

`Drivers/AD9959/ad9959.c` 同时包含：

- 上电、PLL、寄存器写入。
- 单线 GPIO 读回实验。
- Software SPI 测试。
- Direct CW 测试。
- Cyclic FTW DMA 测试。
- SPI1/SPI3 4-bit 双线模式切换。
- GPIO idle pin 重配置。

影响：驱动层不再是稳定的芯片抽象，调试代码、降级代码和目标驱动代码混在一起，修改底层驱动时容易破坏主工程结构。

### C09：编码路径分裂成“一线运行帧”和“双线 DMA 帧”两套

当前存在两套编码 API：

- `Encoder_Encode1Bit()`：生成 `DDS_EncodedFrame`，被 `App/channel_config.c` 和 TIM8 ISR 使用。
- `Encoder_FormatCommand()`：生成 SPI1/SPI3 双线 2-bit 帧，被 `Middleware/Buffer/frame_builder.c` 和各 `mod_xxx.c` 使用。

当前主路径使用前者，目标 DMA 路径和多数 Modulator wrapper 仍使用后者。

影响：同一个调制修改可能只改到其中一套路径；测试通过的路径不一定是目标路径。

### C10：`FrameBuilder`、`TxBuffer`、`Trigger` 保留目标流水线接口，但主程序没有使用

`TxBuffer` 仍有 `spi1/spi3` 双 bank，`Trigger` 仍有 `BSP_SPI_Both_DMA_Start()`、`Trigger_SwapBuffer()`，调试手册也描述 DMA ISR 流程。但当前 `main.c` 没有启动 `Trigger_Init/Start`，也没有在 SPI DMA complete 回调中换 bank。

影响：仓库看起来具备 Phase 2/3 流水线，实际运行路径却是 TIM8 中断重放预编码数组。

### C11：TIM4 时序测量链路当前不可闭合

文档要求 PA0 外部飞线到 PE0，TIM4 ETR 清零，PB6/PB7 捕获 PA15 CS 边沿。当前代码：

- `main.h` 没有 PE0 相关定义。
- `main.c` 没有 TIM4 初始化函数。
- `bsp_tim.c` 的 TIM4 代码引用 `htim4`，但主工程没有该句柄。

影响：调试手册中的 `Trigger_GetCaptureTiming()` 和 TIM8 延迟校准无法在当前工程中真实工作。

### C12：74HC595 文档要求 USART10 半双工，当前实现改成 GPIO bit-bang

引脚文档写 `PE3 = USART10_TX`，595 通过 USART10 半双工单线发送 16 位。当前 `HC595_Write()` 直接用 GPIO 翻转 `OCR_DS` 和 `OCR_SHCP` bit-bang，没有 USART10 初始化和句柄。

影响：不是一定错误，但与文档、接口命名和硬件预期不一致。需要明确最终方案是 USART10 还是 GPIO bit-bang。

### C13：BSP 层已被业务概念污染

目标要求 BSP 不出现 `DDS`、调制、Profile 等业务概念。当前示例：

- `Bsp/bsp_tim.c` include `dds_calc.h`，并使用 DDS 相关时钟常量。
- `Bsp/bsp_spi.c` 写入 `ad9959_diag`。
- `Bsp/bsp_gpio.h` 直接暴露 `BSP_GPIO_DIO2_*`、`BSP_GPIO_IO9959_*`。

影响：BSP 不再是通用 MCU 外设封装，后续更换器件或重构 Trigger 会被业务符号牵住。

### C14：目标模块有骨架但缺实现或未接入

根据架构文档应有完整模块：

- `Drivers/APS6404` 只有 `aps6404.h`。
- `Drivers/Clock` 只有 `clock_mgr.h`。
- `Middleware/Scheduler`、`Packet`、`PulseShaping` 基本是头文件骨架。
- `App/tx_manager.h`、`cmd_parser.h`、`shell.h` 没有对应实现。

影响：当前并未达到文档中的 Phase 3 Scheduler/Packet/Buffer 架构，很多功能只是目录占位。

### C15：上位机协议覆盖范围和目标调制范围不一致

目标支持 CW、ASK/OOK、FSK、GFSK、MSK、BPSK、QPSK、MFSK、AM、FM。当前 `USART1_AD9959_Protocol.md` 和 `host_protocol.c` 只提供 CW、FSK、ASK、BPSK、QPSK、4FSK 命令。

影响：`mod_config.h` 中已有 GFSK/MSK/AM/FM 配置结构和 setter，但不能从上位机协议设置，主链路也没有稳定验证。

### C16：时钟常量和注释不统一

当前文档与代码中出现多组值：

- 协议文档使用 AD9959 SYSCLK `490,909,091 Hz`。
- `dds_calc.h` 宏也固定 `DDSCALC_AD9959_SYSCLK_HZ = 490909091`，但注释里仍有 `511.364 MHz` 等旧值。
- `AD9959_Init()` 调 `BSP_TIM15_SetREFCLK(25000000UL)`，而调试手册写过 `50 MHz PWM`。
- `bsp_tim.h` 注释中 TIM8/TIM15 时钟值和 `dds_calc.h` 的 APB2 timer 常量也不完全一致。

影响：FTW、REF_CLK、PLL、TIM15 ARR 的计算依据不唯一，联调时频率误差难定位。

### C17：根目录混入独立 AD9959 参考工程

根目录存在 `AD9959 Driver Single-bit serial 2-wire mode/`，里面包含 `ADuC7026` 相关源码、Keil 工程、OBJ/LST/MAP/HEX 等构建产物。

影响：这不是当前 STM32H723 工程的一层，容易被误认为可编译源或目标驱动。应作为参考资料归档到 `DOCS/Template1` 或 `Tools/reference`，不要和主工程源码并列。

## 4. 建议修复顺序

1. 先确定唯一硬件主线：恢复 `TIM2 -> DMA -> SPI1+SPI3 -> TIM8`，还是改成 `LPTIM/DMAMUX gate -> SPI DMA -> TIM8`。文档、`.ioc`、BSP、Trigger 必须统一。
2. 把 `main.c` 中 TIM8 ISR 的阻塞 SPI 发送移出，恢复为“ISR/回调只置标志或换 bank”，发送由 DMA 完成。
3. 清理 SPI3/TIM2/TIM4/LPTIM 的 CubeMX 配置和 HAL 句柄，避免保留不可链接的死接口。
4. 拆分 AD9959 驱动：保留正式寄存器/上电/IO_UPDATE API，调试实验路径移到 `Test` 或 `Tools`，用编译开关明确隔离。
5. 让 `Middleware/DDS` 只产出帧，不调用 `AD9959_WriteRegister()`；静态寄存器写入应由 Driver 或 Pipeline 控制层执行。
6. 统一编码路径：选择 `DDS_Command -> 双线 DMA Frame` 作为目标路径，删除或隔离一线降级运行帧。
7. 修正文档中的时钟值、595 传输方式、当前协议覆盖范围，避免联调按旧链路排查。

## 5. 当前状态结论

当前仓库不是 Git 冲突状态，也不是编译失败状态；它的问题是**底层驱动调试过程中引入的降级路径已经成为实际主路径，而目标流水线、文档和旧接口仍保留在仓库里**。

因此下一步不应直接继续改 AD9959 寄存器细节，而应先收敛架构主线：确定最终触发链路、恢复 CubeMX 外设、统一 SPI/Encoder/Trigger，再把调试代码从正式驱动中剥离。

## 6. 2026-08-08 进展：DMA 模式恢复与架构收敛

以下冲突项已在 `Develop_Basic_Buffered_Operation` 分支的 DMA 模式实施中处理：

| 冲突 | 处理结果 |
|:--|:--|
| **C01**（触发链不一致） | 统一为 LPTIM3 → DMAMUX → SPI1 DMA → TIM8 ETR 链路。PA1(LPTIM3_OUT) 飞线到 PA0(TIM8_ETR)+PE0(TIM4_ETR)。文档（CLAUDE.md、trigger.h 注释）已同步。 |
| **C02**（双 SPI DMA 降级） | 恢复 SPI1 单线 DMA 传输。SPI3 双线模式预留后续（与 C09 关联）。 |
| **C03**（BSP 死句柄） | 移除 `extern htim2`（TIM2 已从触发链删除，BSP_TIM2_* 以 `#if 0` 保留）。`htim4`/`hlptim3`/`hdma_spi1_tx` 经 CubeMX 再生后有效。 |
| **C05**（ISR 重活） | DMA 模式 ISR 仅 SwapBuffer+重装 DMA+置标志（~10 行）。编码和符号生成移至 main loop。降级模式 ISR 保留现状不变。 |
| **C09**（编码路径分裂） | DMA 模式使用 `Encoder_Encode1Bit_Direct()` 零拷贝编码（直接写入 D2 SRAM 的 ping-pong 缓冲区，无中间结构无 memcpy）；降级模式保持 `Encoder_Encode1Bit()` → `DDS_EncodedFrame`。两套编码逻辑共享 `build_channel_command()` 调制计算。`Encoder_FormatCommand()` 保留为 SPI3 双线模式备用。 |
| **C10**（流水线未接入） | `Trigger` 模块在 DMA 模式下恢复调用；`TxBuffer` 乒乓缓冲正式使用。 |
| **C11**（TIM4 不闭合） | CubeMX 再生后 htim4 句柄存在；TIM4_CH1/CH2 捕获 PB6/PB7 CS 边沿；ETR(PE0) 硬件清零。`BSP_TIM4_Start()` 在 Trigger_Init 中默认启用。 |
| **C13**（部分） | 移除 `bsp_tim.c` 中的 `#include "dds_calc.h"`（APB2 时钟本地化常量）。其他污染留待后续。 |

**编译开关**：`AD9959_DOWNGRADE_MODE`（0 = DMA 模式，1 = 阻塞 SPI 降级模式）。两种模式在 main.c / dds_control.c / channel_config.c 中通过条件编译隔离。

**关键硬件约束（DMAMUX RequestNumber）**：REQNB 为 5 位字段（最大 32），无法一次解锁 56 字节整帧（4 通道 × 14）。方案：`RequestNumber = 14`（单通道字节数），每个 LPTIM3_OUT 脉冲解锁一个通道，4 个脉冲 = 一帧，全硬件时序。

**实施中新增发现（C18：SPI SSOM / NSS Pulse 错误）**：CubeMX 默认 `NSSPMode = SPI_NSS_PULSE_ENABLE`（= CFG2 的 SSOM 位），导致 CS 在字节之间脉冲。AD9959 多字节寄存器写（CFTW 5B、ACR 4B）会被字节间 CS↑ 中断——**这很可能是历史 commit "传输稳定但是没波" 的根因**（降级模式的 NSSP 同样有害）。已在 `MX_SPI1_Init` USER CODE 段清除 `SPI_CFG2_SSOM`（两种模式均生效）。参考：RM0468 SPI 章节 + AD9959 datasheet 串行协议（寄存器边界自动识别指令字节，单 CS 帧可携带背靠背寄存器写）。

**AD9959 单 CS 帧合法性**：datasheet 原文确认串行端口控制器在寄存器边界自动开始新通信周期（指令字节自动识别），无需 CS 分隔。ADI 参考代码每寄存器独立 CS 帧是 GPIO 模拟 SPI 的软件习惯，非硬件要求。

**IO_UPDATE 设计决策**：采用逐通道 IO_UPDATE（每 LPTIM3 脉冲后一次），datasheet 允许；**不可用 TIM8 ETR 预分频（ETPS=/4）实现每帧一次**——预分频期间计数器自由运行会输出伪 IO_UPDATE。

**未处理项**（留待后续 PR）：C04(Core 业务迁移)、C06(Middleware→Driver 反向依赖)、C07(App 直接操作硬件)、C08(AD9959 驱动拆分)、C12(595 USART10)、C14-C16。
