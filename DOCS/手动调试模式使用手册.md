# 手动调试模式使用手册

> 适用分支：`Develop_Basic_Buffered_Operation`
> 前置条件：`AD9959_DOWNGRADE_MODE = 0`（DMA 触发链，`App/phase1_config.h:28`）
> 代码：`App/debug_manual.h` / `App/debug_manual.c`
> 日期：2026-09-15

---

## 1. 这是什么

一个**运行时开关 + 配置结构体**的调试通道。在 Ozone 里填四个结构体、把一个变量置 1，芯片立刻按你填的内容输出；不用重编译、不用上位机工具、不用重启触发链、不用停机切换。

它的定位是**射频调试台**：反复试频率、幅度、相位、扫频范围的时候，改一个数字就能在 40 µs 内看到结果。

### 与其它两条调试途径的对比

| 途径 | 改参数的方式 | 是否停链路 | 需要什么 |
|:--|:--|:--|:--|
| 上位机 UART 协议 | `SET_*` + `APPLY` | **是** — `Trigger_Stop()` → 写静态寄存器 → `Trigger_Restart()` | 上位机工具 + 会算 CRC |
| Ozone 改 `mod_cfg[]` + `debug_reload = 1` | 手工逐个填 `ftw`（自己算） | **是** — 同样走 Stop/Restart | Ozone |
| **手动调试模式** | 填 `debug_ch_cfg[]`，**填 Hz 不填 FTW** | **否** — 每帧无缝重写 | Ozone |

三种途径的产物是同一条硬件流水线（见 §6），所以调试模式下调通的效果，退出调试模式后由上位机下同样的参数，结果一致。

## 2. 快速上手

```
1. 编译下载，全速运行（不要停下 CPU —— 见 §10 注意事项）
2. 在 Ozone 的全局变量窗口找到 debug_ch_cfg[0..3] 和 debug_manual_enable
3. 填通道配置，例如让 CH0 出 99.7 MHz、满幅、零相位：
       debug_ch_cfg[0].function = 1        // DEBUG_CH_CW
       debug_ch_cfg[0].freq_hz  = 99700000
       debug_ch_cfg[0].asf      = 1023
       debug_ch_cfg[0].pow      = 0
4. 把 debug_manual_enable 置 1
5. 观察 mod_cfg[0].cw.ftw 是否变成 0x33FDE04B（= DDSCalc_FTW(99700000)）
6. 频谱仪上应出现 99.7 MHz 载波
7. 调完把 debug_manual_enable 置 0，把 mod_cfg[] 交还给上位机协议
```

> **至少给一个通道非零 ASF**，否则四个通道全是静音载波，频谱仪上什么都没有（这是设计如此，见 §5.1）。

## 3. 开关变量

```c
/* App/debug_manual.c:14 */
volatile uint32_t debug_manual_enable = 0U;
```

| 值 | 行为 |
|:--|:--|
| `0`（默认） | 调试任务立即返回，`mod_cfg[]` 完全由上位机协议 + `debug_reload` 掌控。行为与没有这个模块时**逐字节一致** |
| `1` | 每帧（25 kHz）用 `debug_ch_cfg[]` 全量重写 `mod_cfg[]`；上位机的 `APPLY` / `STOP_OUTPUT` 被 NACK 拒绝 |

**上升沿副作用**：`debug_manual_enable` 从 0→1 的那一刻，固件会调一次 `SymbolBuf_Clear()`，丢弃上位机此前暂存的符号。目的是防止退出调试模式时那些旧符号突然回放。

**为什么用变量不用 `#define`**：仓库既有惯例（`debug_reload`，`Core/Src/main.c:97`）。Ozone 能在不重编译的前提下改变量，`#define` 不能。

## 4. 配置结构体 `DebugChCfg`

```c
/* App/debug_manual.h:44 */
typedef struct {
    uint32_t function;        /* DebugChFunction */
    uint32_t freq_hz;
    uint32_t sweep_max_hz;
    uint32_t sweep_step_hz;
    uint16_t sweep_dwell_ms;
    uint16_t asf;
    uint16_t pow;
    /* ---- 运行时状态，Task 就地写回，不要手填 ---- */
    uint32_t now_hz;
    uint32_t last_step_tick;
} DebugChCfg;

DebugChCfg debug_ch_cfg[DDS_CHANNEL_COUNT];   /* [4]，每通道一份，sizeof = 32 B */
```

### 字段说明

| 字段 | 类型 | 取值范围 | 单位 | 说明 |
|:--|:--|:--|:--|:--|
| `function` | u32 | 0 / 1 / 2 | — | 0 = OFF，1 = CW，2 = SWEEP。**用 u32 是为了 Ozone 能直接写十进制整数** |
| `freq_hz` | u32 | 0 … 200 000 000 | Hz | CW 频率；SWEEP 时是**扫频起点** |
| `sweep_max_hz` | u32 | 0 … 200 000 000 | Hz | 扫频终点（锯齿回绕点）。CW / OFF 时无意义 |
| `sweep_step_hz` | u32 | 0 … | Hz | 每步频率增量。**0 = 钉在 `freq_hz` 不动** |
| `sweep_dwell_ms` | u16 | 0 … 255 | ms | 每步驻留时间。**0 = 每帧步进一次**（40 µs，即 25 kHz 步进率） |
| `asf` | u16 | 0 … 1023 | — | 幅度比例因子（10-bit）。0 = 静音，1023 = 满幅 |
| `pow` | u16 | 0 … 16383 | — | 相位偏移（14-bit CPOW）。0 = 0°，8192 = 180°，4096 = 90° |
| `now_hz` | u32 | — | Hz | **只读**。扫频当前频率，由任务写回，Ozone 里看着爬 |
| `last_step_tick` | u32 | — | ms | **只读**。上次步进的 `HAL_GetTick()` 快照 |

### 超出范围会怎样

所有字段都会被**钳位**，不会越界写寄存器：

- `freq_hz` / `sweep_max_hz` > 200 MHz → 截到 200 MHz
- `asf` > 1023 → 截到 1023
- `pow` 与 `0x3FFF` 按位与（只有低 14 位有效）
- SWEEP 时若 `freq_hz > sweep_max_hz` → 终点塌缩到起点，变成单频（与工程例程 UI 的行为一致）

### 出厂默认值

```c
/* App/debug_manual.c:21 — 四通道相同 */
{ .function = DEBUG_CH_OFF, .freq_hz = 1000, .sweep_max_hz = 10000,
  .sweep_step_hz = 100, .sweep_dwell_ms = 1, .asf = 0, .pow = 0 }
```

这套值就是工程例程（`DOCS/Template1`）扫频界面的出厂设置：1 kHz → 10 kHz，步进 100 Hz，驻留 1 ms。**ASF 默认 0**，所以刚上电把开关置 1 也不会有射频输出，必须自己填 ASF。

`freq_hz` 默认取 1000（而非例程 CW 界面的 1 MHz）是因为 `freq_hz` 同时充当扫频起点 —— 起点必须小于默认终点 10 kHz，否则一切到 SWEEP 就塌缩成单频。CW 通道反正要自己填频率，这个取舍没有代价。

## 5. 三种通道功能

### 5.1 `DEBUG_CH_OFF`（= 0）— 静音载波，**不是**禁用通道

```
function = 0
→ 频率 = freq_hz（钳位后）
→ asf   = 0
→ pow   = 0
→ mod_cfg[ch] = { CH_MODE_CW, enabled = true, ftw, asf = 0, pow = 0 }
```

这个通道**仍然出现在 14 字节帧里**，仍然参与 DMA 传输，只是幅度为 0，射频上听不见。

**为什么不能真的禁用（`ModCfg_Disable`）—— 会死锁：**

```
全通道禁用
  → Encoder_BuildBank_DMA() 返回 0
  → tx_bank_bytes = 0
  → HAL_SPI_TxCpltCallback 里 if (tx_bank_bytes > 0U) 守卫不成立（main.c:203）
  → 不再 arm DMA → 没有传输完成中断
  → ds.dma_bank_ready 永不置位 → Encoder_BuildBank_DMA() 不再被调用
  → 而 APPLY（另一条退路）在调试模式下已被 NACK
  → 死锁：只能复位
```

（`DebugManual_Task()` 本身已不再挂在这个门控下面——见 §6——所以 `mod_cfg[]` 不会跟着冻住；但链路本身仍然起不来。）

保持通道「在帧里但静音」保证了恒 56 字节/帧，链路永不停摆。所以 `tx_bank_bytes` 在任何调试配置下都恒等于 56，这本身就是一条健康检查。

### 5.2 `DEBUG_CH_CW`（= 1）— 点频

```
function = 1
→ 频率 = freq_hz
→ asf   = asf
→ pow   = pow
```

固件自动算 FTW：

```
mod_cfg[ch].cw.ftw = DDSCalc_FTW(freq_hz)
```

**你填 Hz，不填 FTW。** 换算关系（`Middleware/Modulator/dds_calc.h`）：

```
FTW = round( freq_hz × 2³² / 490 909 091 )
1 LSB = 0.1143 Hz
```

常用频率对照（可直接在 Ozone 里核对 `mod_cfg[ch].cw.ftw`）：

| 频率 | FTW | 十六进制 | 实际频率 |
|--:|--:|:--|--:|
| 1 kHz | 8749 | `0x0000222D` | 999.999 Hz |
| 100 kHz | 874901 | `0x000D5995` | 100 000.03 Hz |
| 1 MHz | 8749007 | `0x00857FCF` | 999 999.95 Hz |
| **99.7 MHz** | **872276043** | **`0x33FDE04B`** | 99 699 999.99 Hz |
| 200 MHz | 1749801491 | `0x684BDA13` | 200 000 000.04 Hz |

> 200 MHz 是上限：AD9959 SYSCLK = 490.909 MHz，Nyquist 是 245.45 MHz，工程例程的 UI 也封在 200 MHz。

### 5.3 `DEBUG_CH_SWEEP`（= 2）— 软件扫频

```
function = 2
→ start = min(freq_hz, 200 MHz)
→ stop  = min(sweep_max_hz, 200 MHz)，若 stop < start 则 stop = start
→ 状态机推进 now_hz
→ 频率 = now_hz
```

**这是 CPU 软件扫频，不是 AD9959 的 LSRR/RDW 硬件斜坡。** 每个驻留周期 CPU 重新算一次 FTW 写进 `mod_cfg[]`，随帧自然流向芯片 —— 与工程例程里用 TIM4 中断改 CFTW 的做法对应，不涉及任何新寄存器。

#### 状态机

```
调用 sweep_step(now_hz, last_step_tick, start, stop)
  │
  ├─ now_hz 越出 [start, stop]  ──→ now_hz = start，重置计时器，返回
  │     （用于：调试器中途改了 start/stop；或退出调试模式后残留的旧值）
  │
  ├─ sweep_step_hz == 0        ──→ 返回（钉在起点不动）
  │
  ├─ (now - last_step_tick) < sweep_dwell_ms ──→ 返回（还没到点）
  │
  └─ next = now_hz + sweep_step_hz
       next > stop ? now_hz = start   ← 锯齿回绕
                   : now_hz = next
     last_step_tick = now
```

#### 时序（默认值 1 kHz → 10 kHz，步 100 Hz，驻留 1 ms）

```
now_hz  1000 ──1000ms──→ 1100 ──1000ms──→ 1200 → … → 10000 ──→ 1000（回绕）
                          每 1 ms 一步 = 1 kHz 步进率
                          走完一遍 91 步 ≈ 91 ms ≈ 11 次/秒
```

#### 驻留时间的实际分辨率

| `sweep_dwell_ms` | 步进率 | 说明 |
|--:|--:|:--|
| 0 | 25 kHz | 每帧一步（帧率 = 100 kHz ÷ 4 通道） |
| 1 | 1 kHz | `HAL_GetTick()` 是 1 ms 分辨率，这是**有效的最小非零值** |
| 255 | 3.92 Hz | 上限 |

> `sweep_dwell_ms` 用无符号减法比较，所以 `HAL_GetTick()` 49.7 天回绕不会造成问题。

## 6. 数据通路与更新率

调试模式**没有**自己的旁路通道。它写入 `mod_cfg[]`，之后与上位机指令走完全相同的路径：

```
DebugManual_Task()                     ← 只多这一步
      │  重写 mod_cfg[0..3]
      ▼
  mod_cfg[]  ◄──────── HostProtocol_Task() + DDSControl_Task()（被 NACK 挡住）
      ▼
Encoder_BuildBank_DMA()                ← 零拷贝直编进 D2 SRAM 的 tx_bank
      ▼
  TxBuf_GetIdle()->spi1[56]            4 通道 × 14 B
      ▼
  (帧完成中断) TxBuf_Swap() + 重新 arm DMA
      ▼
LPTIM3 (PA1, 100 kHz) ──→ DMAMUX 同步门 (RequestNumber = 14)
      │                        └──→ SPI1 DMA → SDIO0 (PD7) → AD9959
      ├─ 飞线 → PA0 (TIM8_ETR) → TIM8 硬件复位
      │        ├─ CH1 (PC6) → IO_UPDATE
      │        └─ CH2 (PC7) → DIO3
      └─ 飞线 → PE0 (TIM4_ETR) → TIM4 复位 → CH1/CH2 捕获 CS↓/CS↑
```

### 更新率

| 量 | 值 | 来源 |
|:--|:--|:--|
| LPTIM3 脉冲率（= 单通道更新率） | **100 kHz** | `P1_BAUD_RATE (100000) × P1_SAMPLES_PER_SYM (1)` |
| 一次 LPTIM3 脉冲传输 | 14 B（一个通道） | DMAMUX `RequestNumber = 14` |
| 完整 4 通道帧 | 56 B / 4 个脉冲 / **40 µs** | |
| `Encoder_BuildBank_DMA()` 调用频率 = 帧率 | **25 kHz** | `ds.dma_bank_ready` 每次帧完成置位 |
| `DebugManual_Task()` 调用频率 | **主循环轮转率**（远高于帧率） | 每轮主循环无条件调用 |

`DebugManual_Task()` **不受 `ds.dma_bank_ready` 门控**——这是刻意的：链路一旦因故障停摆，`dma_bank_ready` 永不再置位，若把调试任务挂在它下面，`mod_cfg[]` 会连同链一起冻结，Ozone 里既看不到也改不动任何参数。放在主循环里之后，`mod_cfg[]` 始终跟随 `debug_ch_cfg[]`，`mod_cfg` 本身就成了链健康度的独立窗口。因为 `Encoder_BuildBank_DMA()` 仍然只在帧完成时执行，所以**每帧进芯片的仍是最新值，Ozone 里改一个数字，最长 40 µs 后到达芯片**，人眼完全无感。

### 每帧全量重写的代价

CW 路径没有状态副作用，同值重锁存不产生毛刺，所以「每帧把四个通道全部重写一遍」是安全的。它带来一个额外好处：**上位机或调试器偷改 `mod_cfg[]` 都会被一个帧周期内覆盖回去**，调试期间状态不会漂。

## 7. 与上位机指令的互斥关系

调试模式的「完全覆盖」体现在两处：**写入点**（每帧重写 `mod_cfg[]`）和**网关**（拒绝会打断链路的命令）。

| 调试开关 | 上位机命令 | 行为 |
|:--|:--|:--|
| 关 | 全部命令 | 现状不变 |
| **开** | `PING` / `GET_STATUS` / `GET_DIAG` | 正常应答（`GET_STATUS` 反映的是调试配置，不是 `pending_cfg`） |
| **开** | `SET_CW` / `SET_FSK` / … | **ACK**，但只写进 `pending_cfg[]`，不生效、无副作用 |
| **开** | `SET_SYMBOLS` | **ACK 并真的写进符号缓冲**，但没人消费它 —— 调试模式下不调 `SymbolSource_Generate()`，缓冲写满后转为 NACK `0x06` BUSY |
| **开** | `APPLY` | **NACK `0x08` LOCAL_MODE** |
| **开** | `STOP_OUTPUT` | **NACK `0x08` LOCAL_MODE** |
| **开** | `debug_reload = 1` | **忽略**（调试任务每帧已经在重建，Stop/Restart 循环只会白白停链然后被覆盖） |

> 调试期间不要指望符号流。开关 0→1 的上升沿会清空符号缓冲，但那只清一次 —— 之后若继续发 `SET_SYMBOLS`，符号会重新堆积到写满为止。

**为什么 APPLY / STOP_OUTPUT 必须 NACK 而不是静默接受**：`APPLY` 会 `Trigger_Stop()` 停掉 DMA 链，然后调试任务在 40 µs 内又把 `mod_cfg[]` 写回去 —— 命令看起来成功了，实际什么都没发生，只是白停了一次链。NACK 让上位机知道真相。

**为什么是 `0x08` 而不是复用 `0x06 BUSY` / `0x07 NOT_READY`**：那两个的语义是「稍后重试」，而这里重试永远不会成功，必须人工退出调试模式。区分开才能让上位机做出正确反应。

**退出路径**：`debug_manual_enable = 0` → 调试任务立即返回 → `mod_cfg[]` 保留最后一组调试值 → 此时再发 `APPLY` 正常生效（`pending_cfg_has_data` 的语义恰好正确：调试期间的 `SET_*` 一直暂存未生效，退出后 APPLY 即接管）。

### CAN 呢？

**当前仓库里没有 CAN 协议代码**：FDCAN1 只有 CubeMX 生成的初始化，Rx/Tx FIFO 元素数为 0，全仓库没有任何 `HAL_FDCAN_*` 调用，也没有中断处理函数。所以「覆盖 CAN 指令」在当前代码上无从体现。

不过覆盖点选在 `mod_cfg[]` / `pending_cfg[]` 的**汇聚处**，而不是 UART 解析层。将来 CAN 指令按同样的模式写 `pending_cfg[]` + 请求 APPLY，会被同一套机制自动覆盖，无需改动本模块。

## 8. Ozone 观察变量清单

| 变量 | 看什么 |
|:--|:--|
| `debug_manual_enable` | 开关本身 |
| `ds.chain_fault` / `ds.chain_fault_count` | 链路故障待恢复标志 / 累计故障次数 |
| `ad9959_diag.chain_recovery_count` | 主循环已执行的自动恢复次数 |
| `debug_ch_cfg[0..3]` | 你填的配置；`now_hz` 在扫频时会自己爬 |
| `mod_cfg[0..3].cw.ftw` | 固件算出来的 FTW，核对你填的 Hz 对不对 |
| `mod_cfg[0..3].cw.asf` / `.pow` | 是否被正确钳位 |
| `mod_cfg[0..3].enabled` | 调试模式下应恒为 `1`（OFF 通道也是） |
| `tx_bank_bytes` | **应恒为 56**。变成 0 = 链路已死 |
| `ds.frame_count` | 单调递增 = 链路在跑 |
| `ad9959_diag.spi1_done_count` | 单调递增 = SPI 传输在完成 |
| `ds.dma_error_count` | 应该一直是 0 |
| `ad9959_diag.dmamux1_csr` | DMAMUX 溢出状态位，非 0 说明同步门配置有问题 |
| `ds.tim4_cs_start` / `ds.tim4_cs_end` | CS↓/CS↑ 捕获，用于校准 TIM8 延时 |

**三条健康检查，扫一眼就知道链路活没活：**

```
tx_bank_bytes == 56  且  ds.frame_count 在涨  且  ds.dma_error_count == 0
```

## 9. 典型调试配方

### 9.1 单通道点频，核对 FTW 换算

```
debug_ch_cfg[0].function = 1        // CW
debug_ch_cfg[0].freq_hz  = 99700000
debug_ch_cfg[0].asf      = 1023
debug_ch_cfg[1..3].function = 0     // OFF，保持静音

debug_manual_enable = 1
```

核对：`mod_cfg[0].cw.ftw` 应为 `0x33FDE04B` = 872276043。

### 9.2 双通道确定性相位差（正交 / 相位扫描）

AD9959 四通道共用同一 SYSCLK，`CPOW` 给出确定性的相位关系：

```
debug_ch_cfg[0] = { CW, freq 10000000, asf 1023, pow 0     }   // 0°
debug_ch_cfg[1] = { CW, freq 10000000, asf 1023, pow 4096  }   // 90°
debug_ch_cfg[2] = { CW, freq 10000000, asf 1023, pow 8192  }   // 180°
debug_ch_cfg[3] = { CW, freq 10000000, asf 1023, pow 12288 }   // 270°
```

相位分辨率 = 360° / 16384 ≈ **0.022°**。改 `pow` 即可连续移相，无需重启链路。

> **CPOW 的语义**：它给该通道的相位累加器输出**加一个固定偏移**，不重置累加器。所以两个通道之间的实际相位差 = 累加器历史相位之差 + CPOW 之差。写 CPOW 只决定了后一项。
>
> 这里四个通道 FTW 相同、同时启动，累加器推进速度一致；但 AD9959 上电后各通道累加器的起始对齐情况**本仓库尚未在硬件上验证过**。如果频谱仪上测出的相位差与你填的 `pow` 差值不符，差值应为常数 —— 记下来，那就是累加器的残余差，填 CPOW 时减掉即可。

### 9.3 扫频观察

```
debug_ch_cfg[1].function       = 2      // SWEEP
debug_ch_cfg[1].freq_hz        = 1000
debug_ch_cfg[1].sweep_max_hz   = 10000
debug_ch_cfg[1].sweep_step_hz  = 100
debug_ch_cfg[1].sweep_dwell_ms = 1
debug_ch_cfg[1].asf            = 1023
```

Ozone 里 `debug_ch_cfg[1].now_hz` 应每 1 ms 加 100，到 10000 后跳回 1000；`mod_cfg[1].cw.ftw` 跟着变。

**改范围不用退出**：直接把 `sweep_max_hz` 从 10000 改成 20000 —— 下一个驻留点就生效，不会重置到起点（状态机只在 `now_hz` 越出新区间时才重新播种）。

**瞬时定位**：想立刻把扫频钉在某个频率上，把 `function` 临时改成 1（CW），`freq_hz` 填目标值，再改回 2 —— 状态机会因为 `now_hz` 越界重新从起点开始。或者直接写 `now_hz`。

### 9.4 四通道独立配置

四个通道完全独立，可以混搭：

```
ch0: CW     99.7 MHz  满幅        载波
ch1: SWEEP  1k→10k    半幅        扫频标记
ch2: OFF    —         静音        占位
ch3: CW     99.7 MHz  ASF=512     −6 dB，用于两音互调测试
```

### 9.5 参数扫描（人手拧）

因为生效只要 40 µs，可以直接在 Ozone 里把 `asf` 从 0 慢慢加到 1023，实时看频谱仪上的幅度变化，做出类似「旋钮」的效果。

## 10. 边界与注意事项

### 必须在运行时改，不能断点

Ozone 支持 live watch（运行时读写变量）。**如果 halt CPU 再改，DMA 链会停**（SPI 的事务在 CPU 停机期间无法完成中断）。改完继续运行即可恢复。用 live watch 窗口，不要用断点。

### 退出时 CPU 应在运行状态

`debug_manual_enable` 置 0 后，`mod_cfg[]` 保留最后一组调试值（不会自动恢复成上位机之前下发的配置）。要恢复上位机控制，退出后重新 `SET_*` + `APPLY`。

### 热复位后的行为

`debug_manual_enable` 是 `.bss` 里的普通全局变量。Ozone 的「复位但保留 RAM」类操作（以及 warm reset）会让它**保持为 1**。`main.c:374/379` 的启动预填里特意在两次 `Encoder_BuildBank_DMA()` 之前都调了 `DebugManual_Task()`，就是为了让这种情况下**第一帧**就是正确的调试配置，而不是先出一帧未初始化的东西。

### 已知不一致（非本模块引入）

`debug_manual_enable` 与 `SymbolBuf_Clear()` 的上升沿检测用的是函数内 `static prev_enable`。warm reset 会同时保留 `prev_enable = 1` 和符号缓冲内容，所以那种情况下不会清符号 —— 但启动预填会立刻把 `mod_cfg[]` 覆盖成调试配置，符号本来也进不去。无实际影响，记录备查。

### 本模块不做的事

- 不碰 REF_CLK（TIM15）、不碰 74HC595、不碰 PLL、不做 MASTER_RESET
- 不支持 FSK / ASK / BPSK / QPSK / 4FSK / GFSK —— 只做例程里的「基础功能」：点频、幅度、相位、软件扫频
- 不实现 AD9959 的 LSRR/RDW 硬件扫频（那需要额外的寄存器配置和不同的写入序列）

要调调制模式，走上位机协议或 `debug_reload` 工作流。

## 11. 故障排查

| 现象 | 原因 | 处理 |
|:--|:--|:--|
| 置 1 后频谱仪什么都没变 | 所有通道 `asf = 0`（出厂默认就是） | 至少给一个通道填 `asf > 0` |
| `mod_cfg[ch].cw.ftw` 不跟着 `debug_ch_cfg[ch].freq_hz` 变 | 开关没置 1；或 CPU 停在断点上 | 检查 `debug_manual_enable`；用 live watch 不要用断点 |
| `tx_bank_bytes` 变成 0 | 通道被真正禁用了（本模块不会造成） | 检查 `mod_cfg[ch].enabled` |
| `ds.frame_count` 停住、`ad9959_diag.spi1_error` 变 `0x10` | 链路故障：SPI 传输错误（典型是 DMAMUX 同步溢出）打断了 DMA，SPI 被 `SPI_CloseTransfer` 关闭 | `AD9959_DMA_AUTO_RESTART = 1` 时主循环会自愈——看 `ds.chain_fault_count` / `ad9959_diag.chain_recovery_count` 是否在涨。设 0 则故障态冻结供检查：读 `hspi1.ErrorCode` / `hspi1.State` / `ad9959_diag.spi1_error` / `ds.dma_error_count` / `ad9959_diag.dmamux1_csr` |
| `ds.dma_error_count` 在涨但链路还在跑 | 溢出被 `Trigger_Stop()`/`Trigger_Restart()` 的同步化压住了，未致命 | 若持续增长，检查 APPLY / `debug_reload` 的频率；仍涨则查 `ad9959_diag.dmamux1_csr` 定位是哪一路 DMAMUX 通道 |
| 上位机 APPLY 回 `0x89 01 00 08` | 正常 —— 调试模式拒绝 | 想用上位机就先 `debug_manual_enable = 0` |
| 扫频不动 | `sweep_step_hz = 0`（这是「钉住」的合法配置）；或 `sweep_max_hz <= freq_hz` | 检查这两个字段 |
| 扫频一步都不走 | `function` 不是 2 | 检查 `function` |
| 频率和频谱仪读数差几十 Hz | FTW 量化误差，1 LSB = 0.1143 Hz | 正常，不是故障 |
| 改完值没反应，但读回来又是对的 | CPU 停在断点上 | 见 §10 第一条 |

## 12. 与工程例程的对应

参考实现：`DOCS/Template1`（康威电子 AD9959 模块，STM32F103RCT6，GPIO 模拟 SPI）。

| 例程功能 | 例程实现 | 本模块实现 |
|:--|:--|:--|
| 点频输出 | 写 CFTW/ACR | `DEBUG_CH_CW` → `DDSCalc_FTW()` + `asf` |
| 幅度调节 | 写 ACR（10-bit ASF + AMP_MULT） | `asf` 字段，上限 1023，编码器固定置 AMP_MULT |
| 相位调节 | 写 CPOW（14-bit） | `pow` 字段，上限 16383 |
| 扫频 | TIM4 中断里软件改 CFTW | `DEBUG_CH_SWEEP` 状态机，每帧推进 |
| 扫频参数 | `SweepMinFre` / `SweepMaxFre` / `SweepStepFre` / `SweepTime` | `freq_hz` / `sweep_max_hz` / `sweep_step_hz` / `sweep_dwell_ms` |
| 频率上限 200 MHz | UI 限制 | `DEBUG_FREQ_MAX_HZ` |
| `SweepTime` 0…255 | UI 限制 | `DEBUG_DWELL_MAX_MS` |

**与例程的两处有意差异：**

1. **不写超界频率**。例程的扫频在步进时先算出超界值再判断回绕，中间那一帧会短暂输出一个超过 `SweepMaxFre` 的频率。本模块先判断再写，不产生这一帧。
2. **不用 GPIO 模拟 SPI**。例程是 F103 + 软件 SPI；本模块走 DMA 硬件流水线，与正式上位机指令完全同路。

## 附录：协议帧速查（字面量，可直接十六进制发送）

用于验证调试模式确实挡住了上位机命令。CRC 已按 `DOCS/USART1_AD9959_Protocol.md` 的 CRC-16/CCITT-FALSE 算好。

```
PING          (SEQ=01)  A5 5A 01 01 00 00 00 E9 CD

SET_CW CH0 99.7MHz ASF=1023 (SEQ=10)
                        A5 5A 01 10 02 07 00 00 20 4D F1 05 FF 03 1F 89
APPLY         (SEQ=20)  A5 5A 01 20 09 00 00 82 12
STOP_OUTPUT   (SEQ=21)  A5 5A 01 21 0A 00 00 66 3D
```

**调试模式关闭时**，APPLY 的应答：

```
A5 5A 01 20 09 00 00 82 12          → CMD=0x09，payload 空 = 成功
```

**调试模式开启时**，同一条 APPLY 的应答：

```
A5 5A 01 20 89 01 00 08 73 DB       → CMD=0x89（NACK 位），payload = 08 LOCAL_MODE
```

注意 CMD 字节从 `09` 变成 `89`（`HOST_FLAG_NACK = 0x80`），payload 长度从 0 变成 1，内容为 `0x08`。

Python 校验脚本见 `DOCS/USART1_AD9959_Protocol.md` 末尾。
